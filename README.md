# ai-codegen-analyst

A small "agentic code-generation" pattern: given a natural-language
question about a dataset, an LLM writes a short Python analysis script,
the script runs safely against a real pandas DataFrame, and if it fails
the agent feeds the real error back to the LLM and asks for a corrected
version — up to a retry limit. It is a workflow where AI autonomously
writes Python scripts for data analysis.

## Scope

- **The dataset is synthetic**, generated by `src/generate_data.py` — a
  motor/personal-injury insurance claims table (Kfz-Haftpflicht,
  Kfz-Kasko, Personenschaden, etc.), with
  deliberately injected data-quality problems (nulls, sign-entry errors,
  inconsistent casing, a sentinel invalid-age value, duplicate rows) so
  the generated analysis code has to handle messy data, not a clean
  textbook table. **It is not real insurer data.**
- **`MockLLMClient` is the only LLM backend actually exercised** by the
  test suite and `run_pipeline.py`. It's deterministic (no network
  calls), and it generates real, runnable Python for a small set of
  recognized question patterns — plus one deliberately broken response
  (an unclosed parenthesis) so the sandbox's error handling and the
  agent's retry loop have a genuine failure to detect and recover from,
  not just uniform success dressed up as "agentic."
- **`RealOpenAIClient` and `RealAnthropicClient` have never been executed
  against a live API in this environment** — there's no `OPENAI_API_KEY`
  or `ANTHROPIC_API_KEY` here. Their call shapes match the real SDKs as
  closely as I could write them without being able to run them. That is
  a weaker claim than "tested against a live API." Both classes raise
  immediately on instantiation without a key, rather than silently
  falling back to mock behavior — see `tests/test_llm_client.py`'s
  `TestRealOpenAIClientFailsFastWithoutKey` /
  `TestRealAnthropicClientFailsFastWithoutKey`.
- **What's genuinely real and fully tested**: the `LLMClient` interface
  itself, the retry-loop orchestration, the two-layer sandbox, and the
  fact that swapping `MockLLMClient` for a real client requires zero
  changes anywhere else — every calling module depends only on the
  `LLMClient` abstract interface, never on a specific vendor SDK.

## Why "AI writes its own code" needs a safety design, not just a demo

Handing arbitrary LLM output to a bare `exec()` is a real security hole,
not a hypothetical one. This project takes that seriously with two
independent, testable layers of defence, both implemented and both
covered by tests — not just asserted in prose:

1. **`src/ast_guard.py`** — a static check that walks the parsed AST
   (not pattern-matching source text, which is trivial to evade with
   formatting tricks) and rejects: any `import`/`from...import`; calls to
   `exec`, `eval`, `compile`, `__import__`, `open`, `input`, `globals`,
   `locals`, `vars`; any dunder attribute access (`().__class__.__bases__`
   — the classic sandbox-escape gadget — is explicitly tested); any
   dunder name access; and any `with` statement (blocks
   context-manager-based escapes via a crafted object). This mirrors the
   same "walk the AST, allowlist only what's needed" discipline used
   elsewhere in my portfolio for `calculator_tool.py`'s safe arithmetic
   evaluator (in `rag-tool-agent-demo` / `rag-tool-mcp-server`), scaled up
   to a much larger permitted grammar since real analysis code needs more
   surface area than a calculator.

2. **`src/sandbox_executor.py`** — even AST-safe code runs in a
   *restricted namespace*: an explicit allowlist of read-only builtins
   built from the real `builtins` module (no `open`, `__import__`,
   `exec`, `eval`, `input`, or anything filesystem/network/process
   related), inside a **separate subprocess** (via
   `multiprocessing.get_context("spawn")`) under a **wall-clock
   timeout**, so a runaway or hanging script can be killed with
   `.terminate()` without blocking or crashing the caller. The DataFrame
   is passed via a temp pickle file rather than through the
   multiprocessing queue directly, to avoid large-object pickling
   overhead on every call.

**Scope note**: this is defence-in-depth appropriate for a
demo/portfolio project showing the *pattern* correctly — it is not a
claim of production-grade isolation. A real production system handling
untrusted code would run it in an actual OS-level sandbox or container,
not just a restricted Python namespace in a subprocess. That distinction
is stated in `sandbox_executor.py`'s own docstring.

## The retry loop

`src/analyst_agent.py`'s `run_analysis()` is what makes this "agentic"
rather than a single prompt-and-run call: it generates code, executes it,
and — if execution fails for any reason (rejected by the safety guard,
a `SyntaxError`, or a runtime error like a missing column) — feeds the
**real error message** back into a new prompt asking for a correction,
up to `max_attempts` (default 3). Every attempt is recorded in the
returned `AnalysisRunResult.attempts` list, not just the final outcome,
so a caller can see exactly what the agent tried.

`MockLLMClient` includes one deliberately broken response (an unclosed
parenthesis, triggered by a "broken"/"syntax_error_test" keyword) so this
retry path is genuinely exercised end-to-end, not just described. When
the retry prompt specifically mentions the injected error ("was never
closed"), the mock returns a real, working correction — the average-claim
calculation the question was actually asking for — rather than
accidentally succeeding via an unrelated fallback response. That
distinction mattered enough to write a dedicated test for it
(`tests/test_llm_client.py::TestMockLLMClientRetryBehavior` and
`tests/test_analyst_agent.py::TestRetryOnFailure::test_retry_produces_a_genuine_correction_not_a_fallback`)
— see "Bugs found and fixed" below for why.

## Project structure

```
src/
  generate_data.py    -- synthetic claims dataset generator
  llm_client.py        -- LLMClient interface, MockLLMClient, RealOpenAIClient, RealAnthropicClient
  code_generator.py    -- prompt builder + code extraction from LLM responses
  ast_guard.py          -- static AST-based safety checker
  sandbox_executor.py   -- subprocess-based sandboxed execution
  analyst_agent.py       -- the retry-loop orchestration
tests/
  test_generate_data.py
  test_llm_client.py
  test_code_generator.py
  test_ast_guard.py
  test_sandbox_executor.py
  test_analyst_agent.py
run_pipeline.py          -- end-to-end demo
```

## Bugs found and fixed during development

Notes from building and testing the project:

1. **Fragile `SAFE_BUILTINS` construction.** An early version tried to
   introspect the ambient `__builtins__` directly, whose type is
   inconsistent (a module at top-level script scope, a dict inside some
   `exec()` contexts). Recognized as fragile before even running it, and
   rewritten to explicitly `import builtins as _builtins_module` and
   build the allowlist from that real module instead — reliable
   regardless of how `sandbox_executor.py` itself is invoked.

2. **Uncaught `SyntaxError` crashing the executor.** Manually testing
   with malformed code (an unclosed parenthesis — the exact shape
   `MockLLMClient`'s deliberately-broken response produces) showed
   `check_code_is_safe()`'s internal `ast.parse()` raising a `SyntaxError`
   that propagated all the way out of `execute_analysis_code()`, crashing
   the caller instead of returning a structured failure. Fixed with an
   explicit `except SyntaxError` clause that returns a normal
   `ExecutionResult(success=False, ...)` — verified by re-running the
   same manual test, which then correctly returned a structured failure.

3. **Retry recovery was accidental, not deliberate.** The first version
   of the retry loop "worked" in manual testing — attempt 1 succeeded
   after attempt 0's syntax error — but only because the retry prompt's
   wording didn't match any of the mock's specific keyword triggers, so
   it fell through to the generic/always-safe fallback response, not
   because the mock was simulating a genuine self-correction of the
   *original* request. That's a real design gap: a retry loop that
   "succeeds" via an unrelated fallback isn't actually demonstrating
   error-driven correction. Fixed by adding explicit retry-detection
   (checking for `"your previous code failed"` and the specific injected
   error text `"was never closed"`) so the mock's retry response is a
   genuine, targeted fix of the original average-calculation request —
   confirmed both by a direct manual re-run and by dedicated tests
   (`test_retry_produces_a_genuine_correction_not_a_fallback`,
   `test_retry_prompt_for_a_different_error_does_not_trigger_the_syntax_fix`
   — the latter checks the fix is scoped to the specific error, not a
   blanket "any retry gets the average-code fix").

## Relationship to sibling projects

This project is a distinct pattern from the agentic tool-use projects
in my related projects (`rag-tool-agent-demo`, `rag-tool-mcp-server`, `rag-tool-api`), which route between a fixed set of *pre-written*
tools rather than generating new code at runtime. The
`LLMClient`/`MockLLMClient` pattern (real interface, tested mock,
never-executed real client) follows the same structure established in
`llm-eval-pipeline`. The AST-based safety-checking discipline follows
`calculator_tool.py`'s safe-arithmetic evaluator from `rag-tool-agent-demo`.
